# 产出物规范

工作目录里的文件是这个想法的**长期记忆**，也是跨会话「推进」的唯一依据。按需创建，不要一次生成一堆空文件。

**何时不要用**：一次性的问答、用户明确只要一个口头答案、想法还在最早期连问题都没定型——这时写文档是负债不是资产。文件是给「还要继续推进的事」用的。

**写完的判据**：一个没参与过这次对话的人，只看文档就知道下一步该做什么。做不到，说明文档在自说自话。

```
idea/
├── README.md        # 一页纸：想法是什么、现在到哪一步、下一步做什么
├── plan.md          # 问题定义 → 方案空间 → 推荐路径 → 里程碑 → 风险
├── glossary.md      # 只放定义，不放实现细节
├── decisions/       # 0001-xxx.md，只记值得记的决策
└── log.md           # 每次推进一行：日期 / 做了什么 / 学到什么 / 下一步
```

（文件名用 ASCII，标题和正文用中文：路径在脚本、glob、grep 里都更安全。）

## 一、先收紧语言，再谈方案

想法模糊，多半是**词**模糊。细化阶段遇到下列情况，**当场**收敛，不要攒着：

- **一词多义**：「用户」指的是付费客户还是使用者？这是两个东西——先分清。
- **和术语表冲突**：术语表里「取消」定义是 X，你现在说的像是 Y，到底是哪个？
- **含糊程度词**：「快」「便宜」「大规模」——换成数字或可验证的判据。
- **同一个东西两个名字**：确认哪个是正式叫法，另一个作为别名记下。

收敛结果**立刻**写进 `glossary.md`，不要攒到会话结束再补。术语表**只放定义**：它不是需求文档，不是草稿本，不放实现细节。

## 二、用具体场景压边界

概念之间的关系靠抽象讨论压不实。**自己造极端场景**把边界逼出来：

中途退款怎么办？两个人都要同一个名额呢？输入为空、超大、重复呢？如果顺序反过来呢？

目的不是回答问题，而是逼用户对**概念之间的分界线**表态。

## 三、决策记录：只在三条件同时成立时才写

1. **难以回头**：以后改变主意的代价是实打实的。
2. **没有上下文会让人困惑**：未来的读者会问「当初为什么这么干」。
3. **是真实取舍的结果**：确实存在别的选项，而你为具体理由选了这一个。

三条缺任何一条，就**不要写**决策记录——否则决策目录会退化成一堆噪音。

写的时候至少包含：背景 / 备选方案 / 决定 / 理由 / 代价与影响 / **什么情况下应该重新审视**。

## 四、方案文档骨架（plan.md）

- **问题定义**：为谁、解决什么问题、**不解决什么**（边界同样重要）。
- **成功标准**：可验证的判据，不是形容词。
- **方案空间与权衡**：至少 2–3 个备选方案，各自的代价。
- **推荐路径**：选哪个、为什么、放弃了什么。
- **里程碑**：每个里程碑必须有**产出物 + 验收标准**，具体到能直接开工。
- **风险与对策**：来自 pre-mortem 与反向头脑风暴的清单。
- **下一步最小行动**：一次一个，且可验证。

## 五、进展日志与复盘（log.md）

- 每次推进写一行：日期 / 做了什么 / 学到什么 / 下一步。
- 定期复盘三问：**什么变了？哪个假设被推翻了？哪个方向该放弃？**
- 计划发生变更时，回到 `plan.md` 改「推荐路径」，而不是让方向在聊天记录里悄悄漂移。

## 六、会话开场动作

开新会话时，先读 `idea/README.md`（没有就从零开始问），再按需读 `plan.md` 与 `log.md`，**接着上次的进度继续，不重复提问已经定过的决策**。若发现文档与实际认知矛盾，直接指出矛盾，而不是默默选一边。
